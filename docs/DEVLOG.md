# DEVLOG

다시 겪지 않아야 할 시행착오와, 다음 판단에 도움이 되는 근거만 남긴다.
작업 이력은 Git, 현재 구조는 [CODE_GUIDE.md](CODE_GUIDE.md), 제품 규칙은 [DESIGN.md](DESIGN.md)를 참고한다.

## 기록 기준

- 증상이나 시도 → 원인 → 해결 또는 기각 이유 → 다음에 확인할 점을 짧게 적는다.
- 단순 기능 추가, 문구·색·간격 수정, 커밋 목록, 테스트 통과 개수는 기록하지 않는다.
- 같은 원인의 사례는 기존 항목에 합친다. 실패한 시도도 재발 방지에 쓸 근거가 있으면 남긴다.
- 과거 구현을 현재 규칙처럼 쓰지 않는다. 해결의 한계나 아직 확인하지 못한 범위를 명시한다.

## 메뉴는 열 때뿐 아니라 레이아웃 변경 뒤에도 배치해야 한다

2026-10-13

- 메뉴를 열 때 한 번만 좌표를 계산하니 창 비율을 바꾼 뒤 버튼과 메뉴가 떨어졌다.
- 기준 버튼을 보관하고 컨테이너 배치가 끝난 `frame_pre_draw`에서 위치를 다시 계산했다. 기준 버튼이 사라지거나 숨겨지면 메뉴도 닫는다.
- 카드 정렬 메뉴는 별도 `CanvasLayer`에 있으므로 `get_global_transform_with_canvas()`로 같은 좌표계에 맞춘다.
- 다음에는 메뉴가 열린 상태에서 창 크기 변경, 화면 가장자리, 기준 버튼 숨김까지 확인한다. 고정 크기 스크린샷만으로는 찾기 어렵다.

## 종횡비 고정과 가로 화면 전환은 다른 요구다

2026-10-13

- PC 화면 비율 고정 요청을 가로 1920×1080 레이아웃 전환으로 해석했다가 롤백했다.
- 창 크기, 콘텐츠 기준 해상도, 화면 방향, 비율이 다를 때의 여백 처리를 구분해야 한다. 기존 세로 UI를 유지하려는 요청에서 기준 해상도를 바꾸면 의도와 달라진다.
- 이 롤백은 기존 설정 복원까지다. 창 자체의 종횡비 제한을 구현했다는 뜻은 아니다.

## UI 정리 중에 학습 동작을 임의로 바꾸지 않는다

2026-10-13

- 앞면의 판정 버튼을 숨기고 ‘답 보기’만 두었다가, 앞면에서도 바로 판정하려는 사용 흐름을 막아 되돌렸다.
- 오답 횟수는 사용자가 앱의 핵심으로 여기는 정보였다. 화면을 간결하게 만드는 과정에서도 제거 대상으로 취급하면 안 된다.
- 다음 카드의 이동·회전·확대 효과는 과했고, 제자리 페이드도 만족스럽지 않았다. 뒷장을 보여주고 다음 카드와 이전 카드의 진입 방향을 구분하는 쪽으로 바꿨다.
- 동작 변경은 시각적 정리와 구분하고, 애니메이션은 정지 화면이 아니라 실제 전환으로 한 단계씩 검토한다.

## 공통 스크립트만으로는 메뉴 모양이 통일되지 않는다

2026-10-13

- 메뉴들이 같은 기반 스크립트를 써도 패널과 버튼 스타일은 개별 씬에 복제돼 있었다. 카드 정렬은 별도 기본 팝업이라 테두리와 선택 표시도 달랐다.
- 공통 메뉴 씬과 패널 리소스로 모으고, 메뉴별로 항목과 동작만 구성하도록 분리했다.
- 재사용 여부를 판단할 때 동작 코드뿐 아니라 씬 구조·테마·아이콘이 실제로 공유되는지도 확인한다. 호버 제거처럼 전체에 적용하는 수정은 개별 override와 평평한 버튼의 기본 테마까지 확인해야 한다.

## 정렬·검색의 화면 순번을 카드 식별자로 쓰지 않는다

2026-10-13

- 필터링이나 정렬 후 화면 행 번호로 원본 배열을 찾으면 다른 카드를 열거나 편집할 수 있다.
- 행은 원본 `card_index`를 유지하고 표시 순서만 바꾼다. 정렬만으로 Markdown이나 학습 순서·이어하기 기록을 수정하지 않는다.
- 검증은 정렬된 목록에서 검색하고, 결과를 실제로 눌러 원래 카드를 여는 순서까지 포함한다.

## 저장 실패에 대비하되 다중 파일 원자성을 과장하지 않는다

2026-10-13

- 기존 파일을 바로 열어 덮어쓰면 쓰기 실패 시 원본을 잃을 수 있다. 같은 디렉터리의 임시 파일에 쓰고 flush한 뒤 교체하도록 바꿨다.
- 덱 이름 변경은 Markdown·진행도·이어하기 파일이 함께 움직인다. 대상 충돌을 먼저 확인하고, 중간 실패 시 이미 옮긴 파일을 역순으로 되돌린다.
- 이 방식은 처리 중 실패에 대한 보호다. 여러 파일을 옮기는 도중 전원이 꺼졌을 때의 완전한 복구까지 보장하지 않는다.

## 시그널 테스트와 실제 입력 검증은 역할이 다르다

2026-07-21, 2026-08-29, 2026-10-13

- 초기 헤드리스 실행에서는 순수 Button도 클릭이 라우팅되지 않은 사례가 있었다. 이후 별도 포인터 검증에서는 헤드리스에서도 통과했다. ‘헤드리스 클릭은 항상 불가능하다’고 일반화하지 않는다.
- `pressed.emit()`은 연결된 동작을 검증하지만, 자식 라벨의 입력 가로채기나 드래그·스크롤 충돌은 확인하지 못한다. 실제 포인터를 사용하는 렌더링 실행을 함께 확인한다.
- 가상 키보드는 display server 지원 여부를 확인하고 닫는다. 편집 취소 시 입력 포커스도 먼저 해제한다.
- 확인창이 `0×0`으로 생성된 사례가 있어, 단순 `visible` 검사 외에 실제 크기와 화면 전체를 덮는지도 확인한다. PC 마우스 검증을 Android 실제 터치 검증으로 간주하지 않는다.

## 에디터의 오래된 버퍼와 임베디드 실행을 주의한다

2026-07-21

- 외부에서 씬을 고친 뒤 F5/F6를 누르자 열린 씬의 오래된 내용이 파일을 덮어쓴 사례가 있었다. 당시 원인은 실행 전 자동 저장이었다.
- 외부 수정 전에는 해당 씬 탭을 닫거나 변경을 다시 불러온다. 실행 후 변경이 되돌아갔다면 에디터 버퍼를 먼저 의심한다.
- 에디터의 Game 탭 안에서는 실행 창이 프로젝트 설정 대신 패널 크기를 따를 수 있다. 창 크기·비율은 별도 실행 창에서도 확인한다.
- 설정 생성 스크립트에서 키를 지워도 `project.godot`의 기존 값은 자동으로 삭제되지 않는다. 설정 제거 시 두 파일을 함께 확인한다.

## 테스트가 멈추면 재시도보다 오류와 노드 경로를 먼저 본다

2026-07-22, 2026-08-09

- C# 시절 씬 노드 타입을 바꾸고 테스트의 옛 타입 캐스트를 남겨, 예외 때문에 종료 코드에 도달하지 못한 적이 있었다. GDScript에서도 노드 경로·타입·파싱 오류를 먼저 확인한다.
- 파일 이동 직후 캐시나 재임포트로 실패한 사례도 있으나, 반복 실행을 해결책으로 삼지 않는다. 로그의 첫 오류를 보고 필요한 경우 import를 수행한다.
- 씬 경로나 타입을 바꿀 때 뷰의 참조와 테스트를 함께 갱신한다. 새 `class_name`의 캐시 의존성을 피해야 하는 독립 검사에서는 스크립트를 명시적으로 `preload()`한다.

## 직접 배치 계산보다 맞는 컨테이너를 먼저 찾는다

2026-07-22

- 덱 타일의 열 수를 직접 계산하던 `GridContainer` 구현은 창 크기 변경 때 문제가 반복됐다. `HFlowContainer`로 바꾸고 줄바꿈을 엔진에 맡겨 해결했다.
- 긴 글자의 줄바꿈은 가로 스크롤 설정과 함께 확인한다. 스크롤 컨테이너가 가로로 확장되면 원하는 줄바꿈이 일어나지 않을 수 있다.

## 데이터의 원문·식별자·설정 필드를 보존한다

2026-07-22, 2026-08-15

- 내용이 바뀌지 않았는데 Markdown을 재직렬화하면 사용자가 맞춘 서식이 사라진다. 가져오기·내보내기·클립보드 생성은 원문을 보존하고, 실제 카드 내용 수정 때만 writer로 다시 쓴다.
- 질문을 진행도 키로 쓰면서 질문 수정 시 기록이 끊기는 문제가 있었다. 인앱 편집은 원본 index와 옛 질문을 보관해 진행도 키를 옮긴다. 영구 ID를 Markdown에 심는 대안은 파일의 단순성을 위해 채택하지 않았다. 외부에서 질문을 직접 바꾼 경우까지 추적하지는 못한다.
- 중복 질문을 삭제할 때는 같은 질문을 쓰는 다른 카드가 남았는지 확인한다. 공유하는 진행도까지 지우면 안 된다.
- 설정 일부를 저장하려고 새 설정 객체를 만들면 나머지 필드를 덮어쓸 수 있다. 기존 설정을 읽고 필요한 필드만 수정해 저장한다.
- 진행도 JSON 형식 확장 때는 옛 숫자 형식과 새 객체 형식을 함께 읽어 기존 오답 기록을 보존했다. 형식 변경은 과거 데이터 fixture로 검증한다.

## 테스트는 표현보다 보존해야 할 계약을 고정한다

2026-08-09, 2026-08-27

- 셔플 결과의 정확한 순서는 계약이 아니다. 원본 배열이 바뀌지 않는지와 카드 개수·구성이 보존되는지를 확인한다.
- 튜토리얼의 문구나 카드 수를 고정하면 문구 수정만으로 테스트가 깨진다. 번들 파일이 파싱되고 실제 학습을 시작할 수 있는지를 검증한다.
- 파일 테스트는 전용 덱과 폴더를 쓰고 설정은 백업·복원한다. 스크린샷용 앱도 저장소를 분리해 실제 사용자 기록을 건드리지 않는다.
